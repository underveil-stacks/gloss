Deploying a service to app-01

Every service runs as a hardened systemd unit on app-01, behind that host's HAProxy, with a backend that listens on loopback and never handles TLS. This runbook covers the whole chain from a merged pull request to a verified version at /about. It assumes you have read the deployment standard and that you can reach the host over SSH.

Merging does not deploy, and neither does cutting a release. The chain is deliberate and has three steps in three repositories; a run that reports success while production stays on the old version almost always means the second step was skipped.1 If you only remember one thing: bump the pin.

Note

The release pipeline cross-compiles on a hosted runner. app-01 never compiles from source, so a missing SHA256SUMS asset fails the play before anything is installed.

The chain at a glance

  1. Tag the service repository. Only a v* tag triggers release.yml.
    1. The gate runs go test, go vet and govulncheck on the latest stable Go.
      1. A vulnerability in a dependency that is not reachable from the binary does not fail the gate.
      2. One that is reachable does, and the fix is a dependency bump, not an ignore rule.
    2. The build publishes one release with linux/amd64 and linux/arm64 binaries.
  2. Bump the pinned version in deploy-config.
    • The pin lives in roles/<service>/defaults/main.yml.
      • The role installs the pinned version, never "latest".
        • A stale pin reinstalls the old binary and the run still goes green.
    • Open a pull request, wait for a named check to conclude, then merge.
  3. Dispatch the Deploy workflow by hand, one service at a time.

Before you start

  • Pull request merged to main and the local checkout synced
  • Migration numbers checked against origin/main for collisions
  • Dry run reviewed, with no unexpected changed tasks
    • HAProxy fragment validates
    • No other Deploy run is in progress on the runner
  • The gateway session told about any actor-facing change

Step 1: tag and release

From a clean worktree on a fresh origin/main. Press ⌃ C to stop the watch once the named check has concluded; a watch that prints "no checks reported" is not a green build.

# Tag from a clean worktree so another session's branch cannot ride along
git fetch origin
git worktree add /tmp/wt-release -b release/v2.4.0 origin/main
git -C /tmp/wt-release tag -s v2.4.0 -m "notes v2.4.0: schedule registry, actor lane"
git -C /tmp/wt-release push origin v2.4.0

# Watch the release; this one line is long on purpose, to show how a code block behaves when a command does not fit the column
gh run watch "$(gh run list --repo example/notes --workflow release.yml --limit 1 --json databaseId --jq '.[0].databaseId')" --repo example/notes --exit-status && echo "released"

if [[ "${DRY_RUN:-true}" == false ]]; then
  export RELEASE_TAG=v2.4.0 RETRIES=3
fi

Step 2: bump the pin

The defaults file says "Bump after each release" for a reason. The change is one line:

@@ -1,7 +1,7 @@
 ---
 notes_user: notes
 notes_listen: "127.0.0.1:8087"
-notes_version: "v2.3.1"
+notes_version: "v2.4.0"
 notes_environment:
   NOTES_LOG_LEVEL: info

The role's unit template is where the hardening lives. Do not loosen it to make a feature work:

# roles/notes/defaults/main.yml
notes_version: "v2.4.0"
notes_listen: "127.0.0.1:8087"
notes_hardening:
  NoNewPrivileges: true
  ProtectSystem: strict
  MemoryMax: 512M
  RestartSec: 5
notes_scrape:
  - job: notes
    path: /metrics

Warning

A redeploy that changes an HAProxy conf.d fragment can fail on the role's inline validate: step. A dry run cannot catch this. Read the run log before retrying.

Step 3: dispatch and verify

This is a production action. Dispatch deploys one at a time; parallel runs race on the runner's shared collections.

Caution

Never run a full client walk against the public edge from your workstation. The 4xx-storm ban firewalls your address, SSH included. Use loopback on the host.

$ gh workflow run Deploy --repo example/deploy-config -f tag=notes -f dry_run=false
✓ Created workflow_dispatch event for deploy.yml at main

$ curl -s https://api.notes.example.com/about | jq -r .version

When it goes wrong

Read the three pillars in order: metrics tell you what broke and when, edge logs tell you which requests, application logs tell you why. A long path such as /Users/operator/src/github.com/example/deploy-config/roles/notes/templates/notes.service.j2 wraps inside its paragraph instead of widening the page.

If this silently stopped working, what would page? The answer must be the name of a rule.

"Be more careful" is not a structural fix.

Tip

A 401 with a 38-byte body in under 150 µs means the request carried no credential at all. A 30-byte body means a bad token. The cadence tells you which client is retrying.

Important

A green step is not proof that it acted. Read the step's log before reporting that a ping, a notification or a write happened.

The health handler

What the play polls after a restart. Go:

// Health reports readiness. It must stay cheap: the deploy polls it every 500ms.
func (s *Server) Health(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 250*time.Millisecond)
	defer cancel()
	if err := s.db.PingContext(ctx); err != nil {
		http.Error(w, fmt.Sprintf("database unreachable: %v", err), http.StatusServiceUnavailable)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(map[string]any{"status": "ok", "version": version})
}

Reference

Inline elements in one paragraph: strong, emphasis, both, the retired Pi-Docker model, inline code, a link within the page, a code link, H2O and E = mc2, and a second footnote.2 Press ⌘ ⇧ P to open the palette.

Pin
The exact version a role installs. Changing it is the only way a deploy changes what runs.
Dry run
An Ansible check-mode pass. It proves the play parses and shows what would change; it does not prove the change works.
Loopback backend
A service listening on 127.0.0.1 only, reachable from the outside solely through HAProxy.
Why three repositories and not one

Version bumps and configuration tweaks would otherwise churn the edge repository. Frontend rules stay with the proxy; backend definitions live as fragments beside the service's role.
